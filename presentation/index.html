Context

The problem at the gate

01

Congestion at entry

Cars queue at the barrier while staff verify identity manually — peak hours create back-ups into the road.

02

No smart check-in

Plate recognition already exists, but there is no conversational confirmation with the driver at the kiosk.

03

Blind slot availability

Drivers enter without knowing when a garage slot will free up — waiting is unstructured.

04

Poor waiting experience

No reliable notification when a slot opens. No-shows and double-claims waste capacity.

Keep this short. The CTO already knows ops pain; the CEO cares about customer experience and throughput.
Solution

Two modules. One brain.

MODULE 01

Kiosk / AI Agent

Voice-driven avatar at each gate. Confirms the customer after LPR + SAP lookup, captures a visit phone if the driver is not the owner, then opens the gate and enqueues them.

MODULE 02

Queue Management

Single shared FIFO queue across all gates. When a slot frees, notifies the next customer (WhatsApp + SMS + app), with a 50-second claim window and fair no-show push-back.

Middleware is the shared brain — talks to LPR cameras, SAP, kiosks, gate controllers, the slot system, and notifications. Every gate feeds one queue.
Stress that we own Module 1 and 2 only. SAP and Slot Availability are existing systems we integrate with.

Module 1 · Kiosk

Known customer — “Is that you?”

01

Car approaches. LPR reads the plate and sends it to the middleware.

02

Middleware looks up the plate in SAP. SAP returns (or webhooks) the customer record.

03

Kiosk avatar greets by name, shows the profile, and asks: “Is this you? Is this your number?”

04

Yes → gate opens. Middleware fires an enqueue event with plate, phone, gate, timestamp.

—

Plate not in SAP → not a client. Gate stays closed. Kiosk directs them to staff.

Align with design doc §2.1. Emphasize gate never opens for unknown plates — security posture for CEO.
Module 1 · Kiosk

Driver is not the owner

01

Customer says the on-file identity / number is not theirs — e.g. a personal driver.

02

Avatar asks: “Are you the owner of this car?” If no → we need this visit’s phone.

03

Driver speaks their phone number. Speech-to-text captures it; avatar reads it back to verify.

04

On confirm → gate opens. Enqueued with the visit-only number. SAP owner record is never overwritten.

WHY IT MATTERS

Queue notifications must reach the person waiting

The account holder’s number is useless if a driver brought the car. We capture a temporary contact for this visit only — then Module 2 can notify the right person when a slot opens.

Retry loop capped; after a few failed confirmations, ops dashboard alerts staff. Touch input can be a fallback if voice fails.

Module 2 · Queue

What the queue system does

01

Know who entered

Every confirmed kiosk visit lands in one shared queue with plate, visit phone, gate, and timestamp.

02

Know slot capacity

Integrates with the existing Slot Availability System — how many slots, which are free, when one opens.

03

Assign fairly

Notify next eligible customer. 50s claim window. No-shows are pushed back further each consecutive miss.

Confirmation source of truth: WhatsApp only. SMS and Toyota app are parallel pings — they do not drive queue logic.
Module 2 · Logic

50-second claim & growing push-back

Start
1 2 3 4
1 times out
2 1 3 4
2 times out
3 1 2 4
3 confirms
3 → slot 1 2 4

Each consecutive no-show for a slot pushes that person one position further than the previous no-show. Distance resets when someone confirms. No retry cap — clients keep cycling until they claim.

Walk the CEO through the pills visually. CTO cares that only one entry is `notified` per slot and that concurrent slots run parallel timers without double-claim.

Engineering

Reliability across N gates

Atomic enqueue & pop

Two gates never corrupt order or double-insert. Two slot-free events never notify the same person or assign the same slot twice.

Single source of truth

No per-gate local queues. Live state lives in Redis; Postgres holds the durable audit trail of every transition.

Idempotent events

Plate re-reads and duplicated webhooks are de-duped by plate + active session so sensors and retries cannot double-enqueue.

Offline fallback

If the kiosk loses middleware mid-flow, it shows “please wait / calling staff.” SAP or middleware down → gate stays closed.
